# Foyer — architecture

## Décisions

**ADR-1 — Rester dans la stack du dépôt.** Le PRD V2 demande de conserver la stack maintenable du dépôt. Celui-ci (Mes Comptes) est une PWA sans framework, sans dépendance d'exécution, publiée sur GitHub Pages. Foyer suit ce modèle, en **TypeScript strict** (`strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `erasableSyntaxOnly`) compilé par `tsc` vers `js/`, servi tel quel. Pas de Next.js/Supabase/Tailwind : rien à héberger, rien à payer, rien qui casse sans réseau. Le JavaScript compilé est versionné pour que Pages le serve ; la CI vérifie qu'il correspond exactement aux sources.

**ADR-2 — Journal d'événements rejoué.** L'état n'est jamais stocké : seul le journal l'est (qui, quoi, quand). L'état est recalculé en rejouant les événements dans un **ordre commun** (horloge de Lamport, puis appareil, puis identifiant). Deux téléphones qui possèdent les mêmes événements obtiennent le même état, quel que soit l'ordre de réception. Chaque événement est **revalidé** au rejeu : s'il est devenu impossible (dernière portion déjà prise, créneau occupé entre-temps), il est écarté avec sa raison et montré comme conflit aux deux. C'est l'équivalent local des « transactions + version attendue » du PRD, sans serveur.

**ADR-3 — Idempotence et annulation.** Identifiant unique par événement : une synchro reçue deux fois n'ajoute rien. Annuler = ajouter un événement `undo` ; avant de le proposer, l'app rejoue le journal sans l'événement et **refuse** l'annulation si une action faite depuis deviendrait impossible (« Sam a depuis déclaré une portion mangée »).

**ADR-4 — Synchro chiffrée par lien.** Lien = journal complet, compressé (deflate), chiffré AES-GCM 256 avec une clé PBKDF2-SHA256 (210 000 itérations, sel aléatoire) tirée du **code du foyer**. Le code ne voyage jamais avec le lien. Fusion = union par identifiant puis rejeu. Tout événement reçu passe une validation stricte (types, longueurs, valeurs) ; tout texte est échappé à l'affichage. Même principe que Mes Comptes, déjà utilisé par le foyer.

**ADR-5 — Quantités exactes.** Fractions d'entiers (`rational.ts`) ; aucun flottant dans un calcul métier. Affichage arrondi seulement à l'écran, signalé par « ≈ ».

**ADR-6 — Dates de calendrier.** Une date est une chaîne `AAAA-MM-JJ` en heure de Paris (Intl, fuseau explicite) ; l'arithmétique se fait en jours entiers ; les instants (ISO) ne servent qu'à l'affichage. Testé autour de minuit et des changements d'heure.

**ADR-8 — Relais chiffré (synchro automatique).** Table Supabase `foyer_relais` (migration `supabase/migrations/`) : chaque ligne = une étiquette de foyer, un appareil, un bloc chiffré. Étiquette et clé AES-GCM sont tirées du code du foyer par PBKDF2 (210 000 itérations) avec deux sels distincts : l'étiquette ne permet pas de déchiffrer. La règle RLS n'autorise lecture et ajout qu'avec l'étiquette dans l'en-tête `x-foyer` ; aucune modification ni suppression. Les téléphones déposent les événements que le relais ne connaît pas encore et relèvent depuis leur dernier numéro ; la fusion reste l'union idempotente + rejeu (ADR-2). Le téléphone mémorise la liste des types d'événements de la version qui a relevé (`SCHEMA`) : si elle change après une mise à jour, il relit le relais depuis le début, pour récupérer ce qu'une ancienne version avait écarté. Sans relais configuré (`src/ui/config.ts`), l'app fonctionne exactement comme avant. En service sur un projet Supabase dédié (`foyer`, eu-west-3) ; la clé de l'app est la clé publique « publishable » (pas un JWT : l'en-tête `Authorization` n'est ajouté que pour une ancienne clé JWT).

**ADR-9 — Import web côté serveur, analyse côté téléphone.** Un navigateur ne peut pas lire la page d'un autre site (CORS). La fonction `supabase/functions/foyer-import` télécharge la page (8 s, 3 Mo maximum, ni adresse IP ni nom local) et n'en renvoie que les données schema.org extraites par `recipe-web.ts`, fichier identique à celui de l'app (un test le vérifie). Le téléphone analyse ensuite les lignes avec le même lecteur que la saisie. Déployée sans vérification JWT par la plateforme (la clé publishable n'est pas un JWT) : la fonction refuse elle-même tout appel sans la clé publique du projet ; CORS limité à l'adresse GitHub Pages.

**ADR-7 — Rien de magique.** Pas d'IA, pas de champ `safe=true`, pas de stock déduit du calendrier, pas de durée de conservation. Les seuls textes sanitaires sont des libellés factuels issus de la fiche DGCCRF citée.

**ADR-10 — Drive Auchan assisté, sans robot.** Pas d'API publique de panier Auchan, CGU hostiles aux robots, et le navigateur ne peut pas écrire chez un autre site : Foyer ouvre des pages Auchan (lien `target=_blank`, aucune requête de Foyer vers auchan.fr, CSP inchangée). L'événement `product.set` retient, pour un ingrédient, une adresse de page produit (format vérifié : `https://www.auchan.fr/…/pr-…`) et une contenance optionnelle ; `drive.ts` en déduit le nombre de paquets en fractions exactes.

**ADR-11 — Catalogue de découvertes en fichier statique, généré en CI.** Le Livre de cuisine de Wikilivres (CC BY-SA 4.0) est lu par l'API MediaWiki dans GitHub Actions (`scripts/catalogue.mjs`, workflow `catalogue`), analysé par `wikibook.ts` (déterministe, testé sur de vraies pages) et versionné en `catalogue.json`. L'app le charge à la demande (`ui/catalog.ts`), le relit (`readCatalog`) et le garde hors ligne (sw.js). Aucun serveur, aucune requête vers Wikilivres depuis le téléphone ; CSP inchangée. Une recette acceptée devient un événement `recipe.save` ordinaire, avec l'attribution dans la note.

**ADR-12 — Rappels en notification sans que le serveur les lise.** Une app web sur iPhone (iOS 16.4+, installée) reçoit des notifications Web Push, mais il faut un serveur pour les envoyer à l'heure. Le téléphone dépose dans `foyer_rappel` l'heure et un bloc chiffré (AES-GCM, clé tirée du code du foyer, données associées `foyer-rappel-v1`) ; `pg_cron` appelle toutes les 5 min la fonction `foyer-push`, qui marque les rappels échus et envoie une notification **vide** (VAPID ES256, clé privée dans le coffre Supabase) aux abonnements du foyer ; le service worker relit les rappels envoyés de son foyer, les déchiffre avec la clé rangée (non exportable) dans IndexedDB et les affiche ; message générique s'il n'y arrive pas (iOS exige une notification visible). Adresses d'abonnement limitées à Apple, Google, Mozilla et Microsoft (contrainte en base et dans la fonction). Rejeté : contenu chiffré dans la notification (RFC 8291) — plus de code serveur pour rien de plus, le texte restant de toute façon illisible pour le serveur.

**ADR-13 — Agenda du mois → repas, par règles fixes et décisions mémorisées.** Une app web ne lit pas le Calendrier de l'iPhone ; elle lit une adresse iCal (Google : adresse secrète ; iCloud : calendrier public ; Outlook : lien publié). Le navigateur ne peut pas la télécharger (CORS) : la fonction `foyer-agenda` la télécharge (fournisseurs connus seulement), la lit avec `ical.ts` (copie exacte, testée) et ne renvoie que les occurrences du mois ; le téléphone les garde en cache local (jamais dans le journal). `agenda.ts` en déduit, sans IA, les présences à changer (mots du titre, chevauchement des heures de repas) ; un seul événement gagne par repas et par personne ; tout changement est une proposition tant que le foyer n'a pas décidé « pareil les prochaines fois » (`agenda.rule`). Les présences posées d'après l'agenda (`agenda.mark`) gardent leur occurrence d'origine : retirées si l'événement disparaît (seulement après une lecture réussie), figées si quelqu'un les modifie à la main. Rejeté : connexion OAuth à Google (validation de l'application, jetons expirant au bout de 7 jours en mode test, rien pour iCloud) ; lecture sur le serveur sans le téléphone (le serveur devrait garder l'adresse et lire les repas : contraire au chiffrement de bout en bout).

**ADR-14 — Une identité visuelle sans images téléchargées.** Chaque plat reçoit un emoji et un fond coloré par règles fixes (`visual.ts`) : rendu immédiat, hors ligne, identique sur les deux téléphones, aucune requête externe (CSP inchangée), aucun droit d'image à gérer. Police Nunito (OFL) servie par l'app. Propositions en cartes (`sheets/deck.ts`) : gestes par événements de pointeur, boutons équivalents pour le clavier et VoiceOver, aucune animation si l'appareil demande moins de mouvement, aucune transparence dans les animations d'entrée (le contraste reste mesurable). Rejeté pour l'instant : photos de plats (pas de source libre fiable pour vos propres plats).

**ADR-15 — Rituel batch et budget : ce que le foyer déclare, rien de plus.** Le rituel (`settings.ritual` : jour et heure des courses, jour et heure du batch) et le batch d'un plat (`prep.batch` : jour où il est cuisiné, distinct du repas où il est servi) sont des événements du journal, donc synchronisés et annulables. Le plat garde son créneau de service : portions, boîtes, restes et courses ne changent pas de calcul ; seuls « la veille / le matin », les rappels et « Pas encore pris » se rapportent au jour du batch. `batch.ts` dérive la vue d'un batch (plats, J+n, boîtes, mise en place commune, ingrédients partagés), ce que le rituel demande aujourd'hui et la série de batchs. Les prix sont un champ du produit retenu (`product.set.price`, centimes, gardé si un téléphone pas encore à jour renvoie le produit sans prix) ; le montant payé est un événement par semaine (`shop.spent`) ; `budget.ts` n'additionne que des prix notés et marque l'estimation « au moins » s'il en manque. Rejeté : durée de conservation calculée (aucune source officielle ne donne une durée par plat maison ; repère [ANSES](https://www.anses.fr/fr/content/comment-bien-conserver-ses-aliments-et-ne-pas-interrompre-la-chaine-du-froid) en lien), ordre de cuisson calculé (pas de durées dans les recettes), prix lus sur auchan.fr (CGU).

**ADR-16 — Nouveautés, aucune redondance, équilibre : des règles fixes et lisibles.** Le réglage `settings.variety` (`max` par défaut quand il est absent, `equilibre`, `mes-plats`) est un événement du journal, partagé par les deux téléphones. `propose.ts` applique toujours les mêmes filtres : un plat jamais deux fois dans la semaine, pas un plat prévu depuis moins de 13 jours s'il reste un autre candidat (sinon il revient, rien n'est laissé vide), pénalité par plat du même genre déjà dans la semaine (`dishType` de `visual.ts`, emoji par mots du nom), découvertes déjà montrées sur ce téléphone (`ui/seen.ts`, 8 semaines, stockage local non synchronisé : c'est une préférence d'affichage, pas une donnée du foyer) placées en dernier. `balance.ts` compte les repères de Santé publique France sur les plats prévus, par personne (la moins servie pour le poisson et les légumes secs, la plus exposée pour la viande et la charcuterie), en grammes par portion à partir des quantités en masse ; une quantité absente est signalée, jamais estimée ; le même compte donne un bonus ou un malus motivé aux propositions. Les durées de préparation et de cuisson sont des champs facultatifs du contenu de recette (`prepMin`, `cookMin`, sans changer le schéma) ; `batchOrder` (batch.ts) ordonne la séance pour une personne qui prépare à la suite pendant que les cuissons tournent (cuisson la plus longue d'abord, règle de Jackson) et n'affiche rien si une durée manque. Révise ADR-15 sur ce point : l'ordre est calculé seulement à partir de durées déclarées. Rejeté : score nutritionnel (pas de table de composition embarquée, risque de fausse précision), IA de suggestion (non déterministe, non sourcée).

**ADR-17 — Prix et qualité sans saisie : données ouvertes figées chaque semaine, aucun appel pendant l'usage.** Deux fichiers statiques, régénérés par la CI (`scripts/prix.mjs`, `scripts/produits.mjs`, workflow `prix.yml`) et servis avec l'app (hors ligne par sw.js) : `prix.json` (prix moyens de vente au détail de l'Insee, API SDMX de la Banque de données macro-économiques, licence ouverte ; séries arrêtées actualisées par l'indice des prix de leur famille ; poids d'une pièce USDA FoodData Central, domaine public) et `produits.json` (produits « vendus chez Auchan » d'Open Food Facts via search-a-licious, prix relevés d'Open Prices, ODbL). Coût d'une ligne (`lineCost`) : prix noté avant la V3.0 › prix relevé du produit conseillé › prix moyen Insee › non chiffré ; le panier dit sa couverture. Qualité par points fixes (Nutri-Score, NOVA, bio, Label Rouge, AOP/IGP), « meilleur rapport » = points − écart au moins cher ÷ 20 %. Le panier suit le menu : `cartChanges` compare chaque coche (`shop.check`, nom de l'article désormais joint, champ facultatif) au besoin actuel, en unités entières pour ce qui s'achète à l'unité. Rejeté : lire les prix ou remplir le panier sur auchan.fr (CGU art. 8 : extraction automatisée interdite sans licence ; aucune API publique ; seul un partenaire comme Jow le fait), appels Open Food Facts depuis le téléphone (quota de 10 recherches/min, User-Agent impossible à fixer dans un navigateur), toute IA (coût en tokens, résultats non sourcés).

**ADR-18 — Factures du drive lues sur le téléphone par pdf.js embarqué, règles fixes vérifiées par le calcul.** Les seuls prix réels d'Auchan accessibles légalement sont ceux de nos propres achats. Le PDF de la facture est choisi par la personne (« Mes commandes › Télécharger la facture » ; une PWA iOS ne peut pas recevoir un partage de fichier) et lu dans le navigateur par pdf.js 6.3.289 (Mozilla, Apache-2.0), build `legacy/` copié dans `vendor/pdfjs/` avec ses empreintes, chargé à la demande (1,8 Mo, jamais au démarrage), sans `eval` : la CSP reste `script-src 'self'` (`worker-src 'self'` pour son worker). `invoice.ts` remet les morceaux de texte en lignes (même page, même hauteur), lit chaque ligne finissant par un montant : quantité × prix = montant, ou poids × prix au kg = montant, sinon « calcul non vérifiable » ; deux montants sans rapport : ligne écartée. Totaux, TVA, frais de service, remises et paiement sont reconnus par expressions précises (« Œufs frais » reste un produit). Rattachement à un ingrédient par mots (singulier, sans accent) : le candidat le plus précis gagne, garde-fou des groupes qualité-prix, égalité laissée à la personne ; elle vérifie tout avant d'enregistrer. Événement `price.paid` (nom imprimé, contenance, prix, vendu au poids ou non, jour) : la facture la plus récente gagne. Données personnelles : seules les lignes portant un montant sont lues, seuls produits, contenances et prix sont retenus. Rejeté : OCR ou IA (coût, erreurs non vérifiables), envoi du PDF à un serveur (données personnelles), lecteur PDF écrit à la main (encodages de polices, flux compressés, PDF chiffrés : pdf.js les gère déjà), lecture de l'espace client Auchan (CGU art. 8).

**ADR-19 — File d'exceptions : l'UI propose, le réducteur dispose.** Une règle par défaut est un réglage (`settings.leftovers`, `boxesFromDinner`), donc un état modifié par des événements, rejoué, synchronisé et annulable ; jamais du code d'interface. Une exception est une fonction pure (`exceptions(r, today, me, now)`), jamais une donnée : aucun événement « exception créée ». Elle disparaît quand l'état devient cohérent. Chaque action est soit une liste d'événements pré-validés (créneaux libres, pas mangés, assez de portions : aucun conflit possible), soit l'écran qui règle. « Plus tard » est le seul événement (`exc.snooze`, par personne, 24 h au plus). Écarts à la spec : `defaults.set` remplacé par `settings.set` (même garantie, pas de second mécanisme) ; « restes posés d'office » = proposés d'office, car un événement émis sans toucher par deux téléphones produirait des doublons et des conflits, et la spec interdit l'état invisible ; « cette semaine » retiré du « plus tard » (contradiction avec la limite de 24 h de la même spec).

**ADR-20 — Semaine générée : un lot préparé, jamais une mutation ; budget tenu par remplacement.** Générer ne touche pas au planning : `proposeWeek` (déterministe) produit des propositions ; `fitBudget` remplace, tant que la semaine dépasse le budget, le plat le plus cher par la première alternative au moins 15 % moins chère dont le prix est bien connu (80 % des ingrédients), une fois par repas ; « Tout approuver » émet les événements habituels, validés un à un par le réducteur, plus `week.discard`. Le brouillon (`week.draft`) est compact (créneau, sorte, identifiant ; 14 au plus) pour rester sous la borne de 20 000 caractères par événement ; relu, il n'écrase jamais un repas rempli entre-temps. Écarts à la spec : pas d'événement enveloppe `week.approve` (le lot d'événements d'une approbation s'annule déjà d'un geste), pas d'approbation jour par jour (les boîtes relient deux jours), pas de saison (aucune source), tags `rapide`/`long` déduits des durées déclarées plutôt que d'un nouvel événement.

**ADR-21 — Reprises Pimzi : allergies, calage, budget à l'accueil, placard ; tout dérivé, rien de deviné.** Allergies et refus : réglage `exclude` de `settings.set` (14 allergènes de l'annexe II du règlement (UE) n° 1169/2011, 20 aliments refusés au plus) ; `allergens.ts` lit le seul nom de l'ingrédient (expressions les plus longues d'abord : « lait de coco » n'est pas du lait, « noix de Saint-Jacques » est un mollusque, « pâté » n'est pas « pâte ») et sépare « contient » (exclu des propositions, vos plats comme les découvertes) de « étiquette à vérifier » (produit transformé : bouillon, sauce, charcuterie — proposé, signalé dans les courses et au drive) ; un aliment refusé se compare mot à mot, « porc » et « alcool » couvrent leur famille. Ce n'est pas un avis médical : l'étiquette fait foi. Calage : médiane des rapports prix payé ÷ prix Insee sur les articles comparables (même unité, sans forme), 5 au moins, bornée à [0,5 ; 2], appliquée aux seules estimations Insee — Pimzi cale par enseigne sans source publique, Foyer sur vos propres factures. Budget et allergies : 4e étape facultative de l'accueil ; aucun montant suggéré (pas de source). Placard : `surpluses` estime le reste d'un paquet pris la semaine précédente (paquets entiers − besoin d'alors, en supposant les plats cuisinés comme prévu) ; la carte « À régler » le propose, « On en a » émet `shop.pantry`, « Plus rien » un `task.set` ; rien n'est déduit sans réponse. Aucun nouveau type d'événement.

**ADR-22 — Portions en plus reprises ; usage compté sur le téléphone, raccourcis à navigation fixe.** Un repas qui prend le même plat qu'un repas cuisiné jusqu'à 6 jours avant, avec des portions « en plus » (ou prêt avec assez de portions libres), devient ses restes (`slot.from`) et les portions en plus baissent d'autant (`prep.extra`) : « 2 + 2 en plus » puis le même plat le lendemain midi = 4 portions, plus 6. Même règle pour « en cuisiner plus » et pour les boîtes d'une semaine générée ; « Cuisiner à nouveau » garde le choix inverse. Aucun changement du réducteur (le rejeu des journaux existants est inchangé). Usage : compteurs par jour (actions, onglets, fiches recette ouvertes) dans `localStorage` (`foyer:usage`), jamais synchronisés, envoyés ni sauvegardés, coupables et effaçables, coupés en mode découverte ; 60 jours gardés. Les onglets ne bougent jamais (l'adaptation qui réorganise ralentit : Findlater et McGrenere, CHI 2004 ; Gajos et al., 2009) : les raccourcis sont des copies dans une zone fixe en haut d'Aujourd'hui (« split menu », Sears et Shneiderman, 1994), recalculés une fois par jour, 4 au plus, épinglables (la personnalisation est préférée à l'adaptation seule). Une recette s'ouvre en fiche de lecture (ingrédients, étapes, allergènes, écran allumé), le formulaire sur « Modifier ».

**ADR-23 — Recettes prêtes partout, comme chez Jow, sans rien inventer.** Le catalogue reste le seul Livre de cuisine de Wikilivres (CC BY-SA 4.0, attribution sur chaque fiche), régénéré par la CI : aucune autre source française sous licence libre vérifiable n'a été trouvée, aspirer un site commercial est exclu et aucune recette n'est écrite par Foyer. Lecture élargie (famille du plat tirée des ingrédients, nombre de personnes lu dans les titres de section, « Par personne », « Donne 10 portions », titres en gras, en définition ou en puce) : 424 plats de repas, dont 181 avec nombre de personnes. Prévoir une recette prête réutilise les événements existants : `recipe.save` (contenu, source, licence) puis `slot.cook` ; une recette déjà dans « Nos plats » passe par `setDish` (mêmes règles, dont la reprise des portions en plus). Aucun changement du réducteur. Le nombre de personnes n'est jamais deviné : une page qui ne le dit pas demande 1 à 8 au foyer avant de prévoir ou d'ajouter, et les idées proposées d'office ne prennent que des pages qui le disent. Classement sans recherche : le même que les propositions de la semaine (`discoveriesFor` : variété, repères d'équilibre, exclusions et allergies) ; avec recherche : les plats correspondants au nombre de personnes connu et non exclus. Le catalogue est préchargé au démarrage (cache du service worker) pour que « Choisir un plat » l'affiche sans attente ; hors ligne sans cache, la section n'apparaît pas. Placé avant « Vos plats » dans le choix d'un plat, sauf réglage « Surtout nos plats ».

**ADR-24 — Factures Auchan : lecture dédiée, vérifiée par deux calculs, calée sans rien garder du réel.** Trois factures Auchan drive du foyer ont été lues par un script qui masque nom, adresse, numéros et téléphone avant tout affichage ; elles ne sont ni versées au dépôt ni gardées. Format relevé : `code · produit · prix U. HT · remise U. HT (facultative) · qté · total net HT · taux TVA · cagnotte (facultative) · total net TTC`. Une ligne n'est retenue que si (prix − remise) × qté = total HT à 1 centime par article près et total HT × (1 + TVA) = total TTC à 1 centime près, avec un taux français (0 ; 2,1 ; 5,5 ; 10 ; 20 %) ; sinon la lecture générique s'applique, puis rien. Prix retenu : TTC net de remise ; la cagnotte gagnée n'est pas déduite. Le nom du produit continue sur la ligne suivante, même après un changement de page : la suite est rattachée si elle commence par une minuscule ou un chiffre, ou porte une contenance ; jamais un « : », une adresse ou un numéro. Date : livraison ou retrait, sinon commande, sinon facture (« Facture éditée le » est le jour du téléchargement). Paiements (« WAAOH », carte cadeau, carte bancaire) écartés. Rapprochement : l'ingrédient doit nommer le produit (deux premiers mots, trois pour un nom composé), la marque en capitales qui précède le nom ne compte pas ; abréviations relevées sur les factures (« PDT », « PLT », « SCISSE », « FROM », « BRIOC »). Contenu du test (`AUCHAN_ROWS`) : entièrement fictif, au même format.

**ADR-25 — Apprendre de l'usage réel : avis après le repas, gênes notées, mode essentiel.** Avis : une carte « À régler » (`avis`), dérivée de l'état comme les autres, pour un plat cuisiné et mangé aujourd'hui ou hier, ni favori ni déjà jugé ; 👍 = nouvelle version de la recette avec l'étiquette « favori » (déjà prise en compte par les propositions), 👎 = `recipe.archive` (rangé : plus proposé, et la recette prête du même nom n'est plus reprise du catalogue, qui écarte vos plats rangés), « Sans avis » = `task.set` sur `avis:<recette>`. Aucun nouvel événement, aucun changement du réducteur. « Ça coince ? » : bouton dans le bandeau collant de chaque écran ; une note = heure, écran, genre (trop long, pas compris, résultat faux, il manque, autre), un mot de 280 signes au plus et les noms des 8 derniers gestes (actions et onglets), dans `localStorage` (`foyer:coince`, 100 notes au plus), jamais synchronisée, envoyée ni sauvegardée ; la liste se copie depuis Réglages pour être transmise. Mode essentiel : batch, budget et bilan, agendas, factures, « déjà au placard ? » ne s'affichent que s'ils servent déjà (rituel réglé, budget fixé ou montant payé, agenda branché, prix payés) ou si ce téléphone les active (Réglages › Fonctions) ; un choix explicite l'emporte ; masquer n'efface rien (données, rappels) et les réglages d'une fonction en service restent accessibles pour pouvoir l'arrêter. Choix par téléphone (chacun son écran), mode découverte : tout affiché.

**ADR-36 — Bilan de la semaine : une fonction pure, des gestes existants.** `core/coverage.ts` (`coverage`) parcourt les repas à venir de la semaine : `servings` (présences, donc agenda appliqué, et invités) > 0 → repas à nourrir, sans plat → manque ; plat à cuisiner dont `portions(...).planned` vaut 0 sur un repas sans personne → plat en trop ; `prep.extra` d'un plat pas encore cuisiné de la semaine et `leftovers` (semaine en cours) → portions en trop. `coverageFixes` ne crée aucun événement nouveau : `fromDrafts` (reprise des portions en plus, qui baissent d'autant, dans `REUSE_DAYS`) puis `slot.move` vers un repas sans plat ; `coverageText` écrit la phrase. Interface : carte en haut de Semaine (`ui/cover.ts`) et demi-phrase après un plat posé ; `dispatch` accepte un message calculé après l'enregistrement (`toast: () => string`). Les changements d'agenda non décidés (`toDecide`) ne sont pas comptés, seulement signalés.

**ADR-37 — Midi nourri par le dîner : une règle, trois usages.** `core/plan.ts` (`fedByDinner`) dit si un midi suit le dîner de la veille : réglage `lunchFromDinner` (tous les midis où quelqu'un mange), sinon `boxesFromDinner` quand tous ceux qui mangent emportent une boîte et sans invité. Le bilan (`coverage` : `fed`, `boxes`, `lunches`, `missing` = plats à cuisiner), la semaine générée (`proposeWeek` : `from` sur le dîner prévu ou proposé) et la pose d'un dîner (`withLunch` : `slot.from` + `prep.extra` réduit, via `fromDrafts`) lisent la même règle ; aucun nouvel événement, un champ de réglage facultatif ignoré par les anciens clients. `paint` (`ui/dom.ts`) garde `selectionStart/End` du champ actif en plus du focus.

**ADR-35 — Dates limites partagées par les menus, l'agenda et les déplacements.** `core/limits.ts` est la seule source : `limits(s)` (produits fermés, DLC ou DDM au jour près, DLC d'abord), `limitFor` (date la plus pressante d'une liste d'ingrédients, `matchesProduct`), `dishLimit(s, k, today)` (DLC à venir d'un plat cuisiné ce jour-là : pas de batch, pas commencé), `lateDishes` (plats prévus après leur DLC). `propose.ts` : bonus +30 (DLC) / +15 (DDM) dans les 3 jours, pour vos plats (`rank`) et les recettes prêtes (`catalogBonus`, avec les repères d'équilibre) ; `proposeWeek` réserve d'abord, par produit pressé d'ici la fin de la semaine, le premier repas ouvert d'ici la date pour un plat qui l'utilise (selon le réglage « Nouveautés »), puis remplit le reste ; les propositions sont rendues dans l'ordre des repas ; `fitBudget` et le réglage « équilibré » ne remplacent jamais une proposition « à utiliser ». `agenda.ts` : `moveFor` rend une liste de `Move` (`dlc`, `room`) : repas libre d'ici la DLC (en avant puis en arrière, repas à venir), sinon échange (le plat sans urgence part au repas libre suivant, deux `slot.move` dans l'ordre), sinon décalage signalé `late` ; `changeText` le dit. `exceptions.ts` (carte `personne`) filtre les repas d'ici la DLC ; `preview.ts` compare `lateDishes` avant/après. Aucun nouvel événement ni état synchronisé.

**ADR-34 — Scan des dates limites : des entrées visibles, pas de nouvel état partagé.** Aucune interface web ne déclenche « Scanner le texte » (Live Text) de l'iPhone : le geste reste « toucher le champ, puis le menu ». Foyer le rend trouvable : bouton dans l'en-tête collant d'Aujourd'hui (`.top`, à côté de « Ça coince ? » ; le raccourci d'usage `a:watchNew` n'est plus affiché pour ne pas doubler), bouton sous celui du drive dans Courses, et rappel `boughtFresh(week)` (`ui/sheets/shop.ts`) : lignes ou articles cochés des rayons boucherie, frais et crèmerie, sans suivi ouvert du même nom. « Plus tard » est un réglage du téléphone (`Device.scanOff`, la semaine écartée), pas un événement synchronisé. La feuille place la zone de scan avant le produit ; les étapes sont rendues tant que le texte n'est pas lu (`readPrinted`), reliées au champ par `aria-describedby`.

**ADR-33 — Couverture des prix : nom d'achat, groupes vérifiés par la CI, mesure hors ligne.** `buyKeys(name)` (`core/refprice.ts`) : clé du nom, puis jusqu'à trois retraits d'un suffixe de préparation en fin de nom (`PREP` : haché, râpé, en dés, sec, du moulin…), puis « oeuf » pour un jaune ou un blanc d'œuf ; `refFor` (Insee) et `groupFor` (Open Prices) essaient ces clés dans l'ordre, le nom exact d'abord. Aucun rapprochement plus large qu'un suffixe retiré. `GROUP_DEFS` passe à 52 groupes ; la catégorie Open Food Facts de chacun est contrôlée par la CI `prix` (nombre de produits et de prix journalisé, écart signalé) ; `setProducts` fusionne par identifiant les clés du code avec celles de `produits.json`, pour qu'une clé ajoutée vaille avant la régénération hebdomadaire. `SEASONINGS` gagne l'eau du robinet, le bouquet garni et le poivre du moulin. `Cart.paidCents` additionne les articles au prix d'une facture : le budget dit la part sûre en euros. Ticket de caisse : pas de nouveau lecteur, le texte scanné par l'iPhone passe par `parseInvoice` (lignes « libellé prix », total vérifié). `scripts/couverture.mjs` mesure sans réseau la part chiffrée (même chaîne que le panier : relevé du produit conseillé, sinon Insee ; `restockCost` pour le quotidien).

**ADR-32 — Dates limites : l'OCR du téléphone, une lecture pure, des suggestions sans état.** Pas de bibliothèque d'OCR embarquée : sur iPhone, « Scanner le texte » (Live Text) insère le texte reconnu dans un champ ordinaire, et `core/printed.ts` (`readPrinted`) le lit : mentions DLC/DDM, formats de date français, confusions O/0 et l/1 entre chiffres, dates d'emballage ou de ponte écartées par leur mention, année absente d'une DLC déduite (`guessedYear`), unités et années absurdes refusées. La saisie reste un `watch.save` (aucun nouvel événement). `core/dlc.ts` (`dlcAdvice`) est une fonction pure de l'état : produit fermé, DLC à 3 jours au plus, rapproché des ingrédients par mots (`matchesProduct`, aussi utilisé par `propose.ts`) ; la date comparée est celle de la cuisson (`prep.batch` sinon le jour du repas). La file « À régler » en tire une carte `dlc` : `slot.move` (échange) vers le repas le plus proche de la DLC, `setDish` d'un de vos plats sur un repas libre, ou `watch.close`. L'alerte « DLC demain » de `watch.ts` s'efface devant cette carte.

**ADR-31 — Lisibilité mesurée, pas jugée.** `e2e/lisibilite.mjs` ouvre le foyer de démonstration (écran 390×844, horloge fixée) et compte, par écran et par feuille : mots affichés (`innerText`), mots du premier écran (nœuds texte visibles dans la fenêtre), éléments touchables visibles (`checkVisibility`, qui ignore le contenu des `details` repliés), petits textes d'explication, et pour Courses la position du premier rayon. Pas de seuil : une mesure à comparer avant et après. Courses place la liste après la seule saisie et le drive ; la feuille « Produits du quotidien » replie le catalogue par groupe (`details[data-g]`, ouverts gardés en mémoire de séance quand une coche redessine la feuille). `html { scroll-padding }` et une marge basse de 10 rem tiennent compte de la barre d'onglets et de la zone des messages.

**ADR-30 — Commande guidée : un toucher par article, sans robot sur Auchan.** Le panier Auchan ne se remplit pas depuis Foyer : aucune interface ouverte au public pour le panier d'un client (seuls les partenaires commerciaux, comme Jow, le font), et piloter la session de la personne passerait par des fonctions internes non documentées. Foyer réduit les gestes de son côté : « ✓ Ajouté · ouvrir le suivant » porte l'URL du suivant (`data-next`) et appelle `window.open(url, '_blank', 'noopener')` dans le gestionnaire du toucher (activation utilisateur ; `wire` empêche la navigation des éléments `data-a`), avant `shop.check` / `restock.bought`. La séance retient les pages ouvertes (`opened`, mémoire de la feuille comme `skipped` et `added`) pour mettre en tête le geste attendu. « 📋 Retenir le produit copié » lit `navigator.clipboard.readText()` sur demande, passe le texte par `productLink` (adresse produit Auchan seulement, paramètres retirés) et émet `product.set` ; refus ou autre contenu : le formulaire s'ouvre. Pas de fenêtre nommée réutilisée : sans `noopener`, la page Auchan garderait un accès à Foyer (`window.opener`) ; avec, la réutilisation n'a pas été vérifiée (iPhone compris).

**ADR-29 — Drive complet : la réserve du quotidien dans la commande et le budget, sans deviner un prix.** Groupes `desserts`, `fruits`, `boissons`, `gouter` dans `core/restock.ts` (aucun d'office), contenance `size` sur les produits dont le paquet est connu. `restockCost` : prix payé (`price.paid`) multiplié par le nombre de paquets payés pour atteindre la contenance (vrac : prix au kilo × poids), sinon prix du produit retenu, sinon relevé Open Prices du groupe, sinon prix moyen Insee (calé sur les factures) × contenance ; un par personne pour le mode « chacun » ; rien sinon. `cartEstimate` et `driveItems` reçoivent la part du quotidien (`RestockPart` : produits dus seuls, et ceux portés par une ligne de recette) : un produit porté par une ligne remplace le coût de la ligne par celui du paquet et la commande par « réserve du quotidien, dont … pour les recettes » ; un produit seul devient l'article `r:<id>`. Le coût par portion reste calculé sur les seules lignes des recettes. « Ajouté au panier » émet `restock.bought` (avec `shop.check` pour une ligne portée).

**ADR-28 — Petit-déjeuner et placard : le même moteur, une seule ligne avec les recettes.** Les aliments rejoignent `core/restock.ts` (groupes `petitdej` et `placard`, aucun d'office) avec un rayon et des clés d'ingrédient. `pairWithRecipes` associe un produit dû à la ligne de recette du même ingrédient encore à acheter (ou un produit acheté à la ligne cochée) : l'écran Courses n'en montre qu'une, le paquet à droite ; la coche porte `data-restock` et émet `shop.check` et `restock.bought` ensemble (décoche : les deux retirés). `deriveShopping` reste inchangé : les besoins des recettes restent exacts, la réserve ne s'y mélange pas. Factures : reconnaissance sur le nom du produit sans la marque (`productName`), motifs ancrés en tête pour les aliments.

**ADR-27 — Produits de la maison : une échéance calculée, jamais un stock.** `core/restock.ts` : catalogue figé de 29 produits (identifiant, rayon Maison & hygiène, mode partage / chacun / foyer, durée de départ, hypothèse écrite, motif de reconnaissance sur facture). Trois événements synchronisés : `restock.set` (suivi, rythme fixe ou automatique, nom d'un produit ajouté), `restock.bought` (achat noté un jour, ou retiré), `restock.due` (date forcée « il en faut / il en reste », valable jusqu'au prochain achat noté après elle). L'échéance se recalcule à chaque rejeu (mêmes événements, même date sur les deux téléphones) : rythme choisi, sinon médiane des 3 derniers intervalles entre passages (achats à moins de 5 jours fusionnés), un seul intervalle : moyenne avec l'estimation, aucun : estimation, premier départ supposé à mi-parcours. Pas de stock ni de quantité restante : seulement des dates d'achat, ce que le foyer sait vraiment. Les lignes ne sont pas des lignes de courses calculées (`deriveShopping` inchangé) : l'écran Courses les ajoute au rayon Maison & hygiène, la coche émet `restock.bought`.

**ADR-26 — Combler les écarts avec les meilleurs sans tiers sur le téléphone.** Photos : la CI prend l'image principale de chaque page Wikilivres retenue (`pageimages`, licences libres seulement), à défaut la première photo du texte de la page, lit auteur et licence sur Commons (`imageinfo`), écarte dessins, petites images, licences non libres et auteurs inconnus, et enregistre une vignette de 500 px dans `img/plats/` (servie par `upload.` ou `thumb.wikimedia.org`) ; les écarts sont comptés par raison dans le journal de la CI ; l'app la sert elle-même (aucune requête vers Wikimedia depuis le téléphone, mise en cache au premier affichage) et montre auteur, licence et source sur la fiche et dans « Crédits des photos ». Une photo douteuse au relu (`validPhoto`) est retirée, la recette reste. Synchro quasi instantanée : après chaque dépôt au relais, un signal vide sur Supabase Realtime (diffusion, protocole Phoenix, canal tiré de l'étiquette du relais) ; l'autre téléphone relève aussitôt. Aucune donnée ne passe par le signal ; connexion ouverte seulement app visible ; refusée ou coupée, la relève toutes les 20 s reste. Vérifiée en navigateur sur un serveur simulé et, sur le vrai relais, par la CI (`scripts/realtime-check.mjs`), le réseau de l'environnement de développement bloquant Supabase. Rappel « Ce soir » : réglage du foyer `evening` (« HHMM », absent = 17 h 30, null = coupé), calculé avec les autres rappels. Pastille : nombre de cartes « À régler » sur l'icône (Badging API, iOS 16.4+, après l'accord des notifications).

## Sécurité et vie privée

- CSP : `script-src 'self'`, `style-src 'self'`, `connect-src 'self'` plus, seulement si un relais est configuré, son adresse exacte ; aucun script ni style en ligne (testé).
- Données : sur le téléphone (localStorage relu après écriture, copies de secours IndexedDB). Avec le relais : seulement des blocs chiffrés de bout en bout ; le relais voit une étiquette pseudonyme, des identifiants d'appareil, des heures et des tailles.
- Rappels : le serveur voit l'étiquette du foyer, l'heure de chaque rappel, un bloc chiffré et l'adresse d'abonnement du téléphone (chez Apple, Google, Mozilla ou Microsoft) ; rappels effacés 2 jours après leur heure.
- Agenda : l'adresse iCal est dans le journal chiffré ; la fonction `foyer-agenda` la reçoit à chaque lecture, télécharge l'agenda, renvoie le mois et ne conserve rien ; les événements lus restent en cache sur le téléphone (`foyer:agenda`), jamais au relais.
- Factures : le PDF est lu dans le navigateur, jamais envoyé ; seuls nom du produit, contenance, prix et jour d'achat entrent dans le journal (donc dans la synchro chiffrée). Nom, adresse, carte de fidélité, numéro de commande : jamais retenus (testé avec de fausses données).
- Hébergement partagé avec Mes Comptes : clés de stockage préfixées `foyer:`, base IndexedDB `foyer`, caches `foyer-*`, service worker de portée `foyer/`. Le service worker de Mes Comptes ne supprime plus que ses propres caches.
- Données personnelles minimales : prénoms, plats, dates déclarées. Sauvegarde JSON lisible (non chiffrée, à garder pour soi) ; liens de synchro chiffrés.
